# Navigation loading feedback

The supplied CRM context displays a branded overlay while navigation is pending. It provides feedback rather than reducing compilation or server response time. Its capture-phase click listener can start a loader for a later-cancelled click; `refresh()` and empty-history back/forward actions can leave the manual state waiting for its arbitrary five-second timeout. That timeout can also hide feedback while a genuinely slow request is still pending. The supplied `/logorbg.png` asset is not present in this website.

The website instead uses Next.js 16's documented `app/loading.tsx` route boundary. `PageLoading` is a small reusable server component with the existing `/logo.webp` key, Dream Key typography, a polite loading status and three gold dots. CSS delays the visual brand reveal by 150ms to reduce flashing on fast transitions; reduced-motion users see static feedback. The fixed fallback adds no document height, uses existing light/future-dark theme tokens, and sits below the shared navigation. It does not capture clicks, lock scrolling or impose a minimum wait.

Next owns the pending lifecycle and removes the fallback when the route resolves, redirects, is replaced by a different navigation or reaches its error handling. Existing Next links, forms, router calls, modifier clicks, external links and same-page anchors keep their normal behavior. No router wrapper or manual click listener is installed. Refreshing an already displayed page can retain its existing content; this loader represents a suspending route boundary, not a general-purpose spinner for every API call or hot reload.

The page routes remain server-rendered. The loader can also appear in the initial streamed response, and does not make the root layout a client component. Next's normal loading-boundary prefetching applies in production; development first-compilation/network delays can still be noticeable.

Verification results are recorded under `output/navigation-loading/`. Live navigation/visual checks remain subject to the preview browser's existing connection-error URL limitation. GitHub CLI authentication and the repository API confirmed that the signed-in account has push permission on `dreamkey-tech/website`, with local branch `redesign`; this request has not committed or pushed the working tree.

Validation passed: production webpack build (including TypeScript), scoped ESLint, Prettier and diff whitespace checks. Production HTTP responses for `/` and `/buy` contain the loading status, a pending Suspense boundary and subsequent streamed page completion; `/login` resolves directly without the fallback. Lighthouse reported accessibility 100 and best practices 96, with no runtime error. Its only failing audit was the existing unauthenticated `/api-proxy/v1/user/auth/me` 401 console response. These checks verify build and streamed delivery, not the visual timing of client-side transitions.


## Property listing feedback — 3 November 2026

Buy links deliberately retain `prefetch={false}` because property details are authenticated. `components/property/PropertyLinkPending.tsx` reads Next's `useLinkStatus` inside the real listing Link and portals the existing branded loader to the body with “Opening property…”. This covers the response-start wait without clipping inside photo cards or introducing invalid heading markup. Prevented anonymous clicks still open Login; modifier/new-tab/download links keep their existing behavior. The existing 150ms content reveal/reduced-motion styles are reused, without a minimum wait or manual timeout.

`app/buy/[slug]/loading.tsx` adds a property-specific streamed loading boundary. After OTP success, the persistent Buy `PropertyAccessProvider` uses a native React transition around the existing push/refresh continuation and shows the same status while navigation is pending. The popup itself can close without unmounting its pending feedback. Native navigation resolves or cancels the feedback; no global click interception or request changes were added.

The server detail GET is awaited before rendering (existing 15-second abort limit). The CRM interest POST starts only after the authorized detail content mounts and does not gate the content. No live backend timing was measured, and the loader is feedback rather than a claim of a faster API. Authentication cookies, redirects, API payloads, interest retry/deduplication and analytics remain unchanged. Four actual-source loading checks and the ten existing property/auth regressions pass. The loading harness exercises real React Suspense/useTransition while its fake route is held pending, then verifies removal after completion; Link context, transport and visibility are isolated. Scoped ESLint, TypeScript and the production webpack build pass. Evidence is in `output/navigation-loading/property-loading-verification.json`; actual browser timing/live backend behavior was not measured, and production testing is left to the user as requested.
